# ADR 0004: редагування поточного стану зі збереженням версій

Статус: прийнято, 2026-11-04. Застосунок 0.4.0, HTTP/MCP/JSONL протокол v1.

## Рішення

Люди та агенти можуть виправляти робочі дані через одну команду `resource.update`.
Поточна проєкція редагується; повні попередній і новий стани залишаються в
незмінному `resource_revisions` з editor, часом та необов'язковою причиною.
Це уточнює попереднє правило незмінності findings/verifications/submissions:
незмінними є походження, історичні версії та subject перевірки/відправлення.
Автор первинного запису не стає автором чужої правки.

Редагуються projects, actors, challenges, tasks, findings/README, flags,
verifications, submissions, messages, artifacts (метадані) та власний activity.
UUID, project_id, первинні автори, час створення, credentials, event journal,
історичні revisions і службові поля lease не входять до editable fields.

Кожна правка вимагає актуального expected_version; конфлікт дає 409, форма
зберігає введену чернетку. Revision, зміна, подія та ідемпотентна відповідь
комітяться разом під наявним project lock. Повтор ключа не дублює історію.
Revision має типізований project-scoped FK до цілі та FK до editor, включно
з DB-перевіркою відповідності collection/resource_id. Значення правки не
потрапляють у загальний event stream.

## Доступ

| Запис | Хто редагує |
| --- | --- |
| CTF і перевірки флагів | owner/coordinator |
| Учасники | owner; кожен також власне ім'я й спеціалізації |
| Challenge | учасник з правом роботи |
| Task | creator, assignee, owner/coordinator |
| Finding, flag, submission, artifact metadata | первинний автор або owner/coordinator |
| Повідомлення | лише відправник; адресат не змінюється |
| Activity | лише власник identity |

Останнього активного owner не можна деактивувати чи понизити. Kind identity
не редагується, агент не створює human identity. Зміна consent policy артефакту
залишається дією людини. Observer може змінити власне ім'я/спеціалізації та
звіт activity, але не спільні матеріали. Backend повертає дозволені поля у
`get_resource.editing`; frontend використовує той самий schema contract.

Редагування task не краде чинний lease іншого агента. Для running потрібні
claim/renew, для review — окремі людське рішення/start/report. Перенесення
task між challenges атомарно переносить пов'язані findings зі збереженням
їхніх авторів та окремими revisions.

Приватний message resource та його історію можуть читати відправник і адресат;
outbox уже надавав відправнику той самий вміст. Адміністративна роль не відкриває
чужі приватні розмови. Broadcast читають учасники проєкту.

## Повідомлення, флаги та файли

Receipt тепер стосується `message_version`. Після правки старе processed не
підтверджує новий текст. Для message.version >1 acknowledgement вимагає
expected_version. Receiver використовує окремий ключ receipt на версію,
checkpoint hook повторно доставляє змінений текст, а старий pending JSONL
packet інвалідується. Обробка старої версії, що прийшла в одному event batch
із новою правкою, не прибирає нову версію з контексту чи черги receipts.
Повідомлення не можна «забрати з пам'яті» того, хто вже його прочитав.

Зміна value/challenge/target/round флага скидає поточне підтвердження. Verification
і Submission містять незмінний subject зі значенням та scope перевіреного флага.
Міграція заповнює subject старих записів за тодішнім незмінним Flag. Виправлення
останньої чинної verification узгоджує поточний Flag; виправлення історичної
перевірки попереднього значення не підтверджує новий флаг. Submission outcome
залишається окремим від verification.

Змінені байти — новий Artifact UUID з supersedes_id та власними review/дозволами.
Опубліковані старі байти, SHA-256, звіти та посилання залишаються доступними за
старим UUID. Версії утворюють лінійний ланцюжок: друге конкурентне продовження
одного source відхиляється. Upload вимагає expected_version джерела й перевіряє
право редагування; передача байтів відбувається поза DB lock. Веб має текстовий
редактор і завантаження нового файла, MCP — publish_artifact із supersedes_id.
Захист requires_review успадковується, старий дозвіл не дає доступу до нових байтів.

## Сумісність

Alembic `a8b6231d5e90` додає versions, revisions, subject, supersedes_id та
message_version receipt. Старі значення починаються з version=1. Хеші старих
message.ack без expected_version збережено, поки повідомлення не редагували.
Старі UUID/байти/команди залишаються дійсними; нові можливості потребують клієнта
0.4.0. Старий клієнт отримає зрозумілий конфлікт при спробі ack нової редакції.

Локальний SQLite cache переходить із schema 0/1 у 2 без втрати подій/курсора.
Адаптери 0.3 відмовляються відкривати новий cache; після оновлення MCP/receiver
потрібно перезапустити процеси. Delivery/event envelope v1 не змінюється.

Історія за замовчуванням обмежена бюджетом і містить уривки полів; revision_id
дозволяє явно прочитати одну повну правку. Моделі не повинні отримувати весь
журнал або всі схеми заради одного виправлення.
