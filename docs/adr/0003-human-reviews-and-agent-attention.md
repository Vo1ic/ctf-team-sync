# ADR 0003: рішення людини, адресні роботи й увага агента

Статус: прийнято, 2026-11-04. Застосунок 0.3.0, доменний протокол v1.

## Рішення

Залишаємо FastAPI, PostgreSQL, спільні команди й наявний event journal.
Без окремої черги, сервісу моделей, акаунтів чи синхронізації каталогів.

Аналіз артефакту є спеціалізованою Task з `kind=artifact_review` та посиланням
на Artifact. Lease і версії залишаються спільними для всіх робіт.

1. Людина додає файл, фото або текст через веб. Текст стає незмінним `.txt`;
   завантаження з вебу має `requires_review=true`.
2. Людина може номінувати агента або залишити відкриту роботу. Агент бере її,
   сервер фіксує ім'я та надсилає запит людині. У проєкті одночасно дозволений
   один незавершений review на артефакт.
3. Людина-автор завантаження або людина з роллю owner/coordinator вирішує
   `approved/declined`. Рішення потребує поточної версії та чинного lease.
   Агент не може схвалити аналіз, навіть маючи owner. Agent-owner також не може
   видати нову human identity. Це межа credentials, а не доказ фізичної присутності
   людини: людський токен не слід передавати агенту.
4. Агент явно виконує `artifact.review.start`, тоді отримує захищені байти.
   Для кожного GET content перевіряємо його власний чинний approved/start lease.
   Інший агент потребує окремого рішення. Release/зміна адресата скидає дозвіл.
5. `artifact.review.complete` вимагає README; результат є Finding з автором,
   artifact_id і task_id. Звичайний `task.complete` цей крок не обходить.
6. `unusable` потребує причини та архівує матеріал. Байти зберігаються: людина
   може завантажити й відновити артефакт. Прямий архів людиною закриває незавершені
   reviews; відновлення не поновлює старі дозволи.

Сервер не запускає LLM, не доводить якість README й не перевіряє, чи агент
прочитав локальну копію до завантаження. Дозвіл стосується серверної видачі байтів.
Агент працює у своїй CLI/IDE; доступ до MCP сам по собі не пробуджує сесію.

`requested_assignee_id` — адресат, `assignee_id` — виконавець чинного lease.
Нову роботу можна адресувати людині або агенту. Лише адресат може взяти зарезервовану
роботу; creator/lead змінює адресата, якщо немає чинного lease. Номінація не
означає прийняття. Фактичні зовнішні дії lease не зупиняє.

Імена identities стабільні й не залежать від провайдера. Порожнє ім'я агента
отримує короткий псевдонім; збіги імен при створенні/перейменуванні — числовий
суфікс під project lock. UUID залишається ідентичністю; старі збіги імен не переписуємо.

Activity — останній явний звіт/дія з TTL 30–600 секунд (автоматично 120).
Показуємо `idle/working/waiting_human/blocked/ready`, деталь, роботу, час та
прострочення. Після human approval стан `ready`, поки сам агент не почав аналіз.
Receiver не підтримує вигадану зайнятість stopped-моделі. Свіжість обчислює сервер;
веб враховує різницю годинників і оновлює стан через наявний long polling.

## Повідомлення та перевантаження

- Однакові sender, recipient, body та всі typed metadata протягом 60 секунд
  дають той самий message ID і `duplicate_count`; новий ключ команди збільшує
  лічильник. Ідемпотентний replay його не збільшує. `deduplicate=false` дозволяє
  свідомий повтор. Різні автори не об'єднуються.
- `kind=status` з однаковими автором, адресатом, task та `group_key` залишає
  у поточній увазі лише останній статус. Після його processing старі не виникають
  знову. Запитання/доручення не згортаються за подібністю тексту.
- `expires_at` прибирає повідомлення з attention, зберігаючи inbox та receipts.
  Службовий запит дозволу також зникає з актуальної уваги після рішення іншої
  людини, release або спливання lease; це не створює удаваного processed receipt.
- До 120 sends/duplicates за хвилину на actor, з них до 20 urgent. Відповідь 429
  містить Retry-After. Службові доручення й запити агента теж враховуються;
  явні рішення людини та receipts залишаються доступними при перевантаженні.
- `reply_to_id` перевіряє доступ до попереднього повідомлення; до восьми повідомлень
  у ланцюжку. Це обмежує явний ping-pong, але не доводить відсутність циклу, якщо
  клієнти починають нові threads або не передають reply metadata.
- `attention` чергує авторів у межах priority і виділяє один normal слот на три
  urgent. Це окрема read-only проєкція, а не видалення чи processing історії.

Checkpoint hooks використовують останній durable attention snapshot перед FIFO
подіями стану. Повторне вставлення вже виданих message IDs у тій самій сесії
пригнічується після stdout flush; replay скидає цей локальний стан. Snapshot
обмежено 50 актуальними повідомленнями; агент повинен явно опрацьовувати їх,
перечитувати attention і сторінки. Нове urgent не чекає програвання всього
історичного journal. Обмежений розмір контексту залишається явним компромісом.

JSONL `context/read` зберігає стабільний FIFO пакет до explicit ack; курсор не
переставляємо за пріоритетом. Для актуальної уваги є `messages/attention`.
Старий сервер без endpoint зберігає попередню FIFO поведінку receiver/hooks.

## Сумісність і міграція

Міграція `9c1e7a302b44` додає колонки та Activity; старі задачі залишаються `work`,
старі файли — спільними без нового дозволу, повідомлення — `note/normal`.
Протокол/event envelope v1 зберігається, додаються типи подій і поля відповідей.
Хеші команд зі старими аргументами збережено для повторів після оновлення.
Події дубліката `message.duplicate` не створюють нове тіло в старому receiver.
Нові можливості агента потребують оновлення його MCP/адаптера до v0.3.0.

Наступне розширення робимо за спостереженнями: спершу зручні шаблони README та
огляд прострочених доручень. Семантичне злиття повідомлень, складні графи робіт,
автоматичне виконання довільних завантажень і постійний heartbeat моделі не додаємо.
