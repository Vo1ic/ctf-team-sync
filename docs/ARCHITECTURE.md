# Архітектурний фундамент v1

Статус: початкова реалізація. Проєкт незалежний від конкретного CTF-workspace,
моделі, ОС, редактора та провайдера LLM. Зміни інваріантів потребують окремого ADR,
плану міграції та перевірки сумісності. Це правила еволюції, а не заборона розвитку.

## Інваріанти

1. **CTF-проєкт є межею даних і доступу.** Кожна доменна сутність належить одному
   проєкту. Посилання між різними проєктами заборонені також зовнішніми ключами БД.
   UUID стабільні та не залежать від імен, локальних шляхів, ОС чи моделі.
2. **Сервер зберігає узгоджений стан.** API, MCP та майбутній UI виконують ту саму
   бізнес-логіку. Адаптери не підключаються до БД і не створюють власних правил.
3. **Команда, зміна, подія та запис ідемпотентності — одна транзакція.** Повтор тієї
   самої команди з тим самим ключем і виконавцем повертає попередній результат.
   Інший вміст із тим самим ключем дає 409. Невдала команда не створює події.
4. **У кожному проєкті події впорядковані за commit.** Курсор — `seq` в межах
   проєкту; timestamp не використовується для порядку. Повторна доставка допустима,
   споживач зберігає курсор після обробки. Гарантії exactly-once для зовнішніх дій немає.
5. **Робота має одного актуального виконавця.** Призначення є lease зі строком дії.
   Взяття, поновлення і завершення перевіряють версію; поновлення та завершення
   також перевіряють власника й чинність lease за годинником БД.
6. **Результат має походження.** Знахідка містить автора й докази; правки мають
   незмінні before/after revisions та окремого editor. Перевірка флага
   відокремлена від повідомленого результату відправлення. Читання повідомлення
   не є підтвердженням його опрацювання.
7. **Опубліковані файли незмінні.** Артефакт ідентифікується UUID та SHA-256.
   Інша версія файла — новий артефакт. Локальний шлях не є спільним ідентифікатором.
8. **Можливості клієнта оголошуються явно.** MCP-доступ, приймання мережевої події,
   передавання в контекст і запуск нового кроку моделі є різними можливостями.
   Система не обіцяє пробудити будь-яку CLI/IDE через один лише MCP.

## Домен

- `Project`: профіль `jeopardy`, `attack_defense` чи `custom`, правила та можливості.
  Профіль описовий; доступність флагів визначає `capabilities.flags`.
- `Actor`: людина або агент, проєктна роль, можливості, стан доступу. Кожному
  незалежному одночасному виконавцю потрібна окрема agent identity. Модель та її
  локальні скіли не визначають identity. Агент може посилатися на людину-власника.
- `Challenge`: зовнішнє завдання змагання. `Task`: окрема робота команди,
  з необов'язковим посиланням на challenge. Один challenge може мати багато tasks.
- `Finding`: версійоване спостереження, гіпотеза, результат або невдала спроба,
  з доказами та необов'язковими посиланнями на challenge/task.
- `Flag`: значення, challenge, ціль, раунд, строк дії та поточна перевірка.
  Дублі визначаються за `(project, value, challenge, target, round)`; строк дії
  не змінює тотожність флага. Сам флаг не є звичайною нотаткою.
- `Submission`: версійований звіт із незмінним subject флага. Прийняття платформою,
  відхилення та невідомий результат — різні стани. Автоматичного відправлення немає.
- `Verification`: версійований запис із незмінним subject. Нова перевірка оновлює поточний
  стан Flag, але попередній висновок, автор, метод і докази залишаються в історії.
- `Message`: адресоване повідомлення або broadcast. Receipt належить конкретному
  отримувачу та може рухатися `received → processed`. `processed` є явним
  підтвердженням клієнта; сервер не доводить розуміння тексту моделлю.
- `Artifact`: метадані незмінного файла. Посилання в доказах: `artifact:<uuid>`.
- `Event`: незмінний конверт зміни зі schema version, автором і resource ID.
- `Command`: результат команди для безпечного повтору після невідомого результату запиту.

Стани task у першій версії: `open → running → done`; прострочений `running` можна
перевзяти, збільшивши версію. Залежності, блокування, скасування, призначення іншому
агенту та службові сесії додаються окремими командами й міграціями.

З 0.2 є явний `task.release`: власник чинного lease з поточною версією атомарно
створює handoff finding із причиною та повертає роботу в `open`. Нових станів
чи колонок немає. Див. [ADR 0002](adr/0002-agent-workspace-and-browser-access.md).

З 0.3 є адресат роботи окремо від виконавця, artifact review з рішенням людини
та README, відновлюваний архів, короткі імена, Activity з TTL і attention-проєкція
повідомлень. Додаткового сервісу моделей/черги немає. Правила дозволів, дедуплікації
та сумісності — у [ADR 0003](adr/0003-human-reviews-and-agent-attention.md).

З 0.4 поточні робочі записи редагуються через resource.update з версіями та
незмінною історією правок. Артефактні байти змінюються через новий UUID із
supersedes_id; новий вміст має власний дозвіл. Receipts прив'язані до редакції
повідомлення. Див. [ADR 0004](adr/0004-versioned-resource-editing.md).

Lease захищає спільний стан сервера, але не вимикає старий агент і не зупиняє його
дії щодо зовнішньої цілі. Для таких дій потрібні кооперація клієнтів або окремий
керований виконавець. Система не гарантує припинення процесу після втрати мережі.

## Авторизація і координатор

Bootstrap credential може лише створити проєкт і його першого owner. Для подальшої
роботи повертається окремий проєктний credential. В БД зберігається SHA-256 випадкового
256-бітного токена; відкритий токен повертається лише під час видачі. Owner створює
інші identities та відкликає доступ; останнього активного owner відкликати не можна.

| Роль | Повноваження першої версії |
| --- | --- |
| owner | Читання, робочі команди, перевірка флагів, видача та відкликання доступу |
| coordinator | Читання, робочі команди, перевірка флагів |
| worker | Читання, роботи, знахідки, флаги-кандидати, звіти відправлення, повідомлення |
| observer | Читання, підтвердження власних повідомлень, власне ім'я та звіт Activity |

Координатор може бути людиною або агентом. Він створює роботи та передає доручення
через повідомлення; виконавець бере lease на себе. Власного циклу LLM на сервері немає.
Втрата координатора не зупиняє сервер. Координатор не обходить версії та leases.

Всі учасники проєкту бачать його колекції, включно з флагами. Inbox приховує тіла
особистих повідомлень від інших identities. Журнал подій містить ідентифікатори
та метадані зміни, без токенів, значень флагів чи тіл повідомлень. Проєктний журнал
все одно розкриває факт і автора операції; це не ізоляція метаданих між учасниками.

## Транзакції й доставка

Реалізація v1 — модульний моноліт FastAPI + PostgreSQL. Кожна коротка команда
блокує рядок проєкту `FOR UPDATE` перед змінами. Це одночасно серіалізує команди,
захищає lease і забезпечує порядок commit для event sequence. Короткі читання
беруть `FOR SHARE`, щоб snapshot і event batch мали узгоджену межу. Мережеві
очікування та передача файлів не утримують ці блокування.

Це свідомий компроміс для командного навантаження. Шардинґ блокувань або окремий
event broker додається лише після вимірювання; порядок і гарантії зберігаються.

Журнал у PostgreSQL є джерелом подій. API надає batch replay, long polling до 25 с
та власний SSE endpoint із `Last-Event-ID`. SSE — транспорт доставки, а не черга.
Після обриву клієнт читає все після останнього обробленого `seq`. Немає залежності
від пам'яті процесу, тож перезапуск API не знищує повідомлення чи курсори журналу.
Споживачі зберігають власні курсори; автоматичної очистки журналу у v1 немає.

Семантика блокувань спирається на [документацію PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html).

Події є сповіщеннями та аудитом операцій, а не повним event sourcing. Вони не
містять повного стану кожної сутності; актуальні дані читаються через колекції.
Невідомі поля envelope потрібно ігнорувати. Невідому schema version слід зберегти
для повтору та показати як несумісність, не мовчки підтверджувати як оброблену.

Bootstrap повертає огляд і перші 100 actors/challenges/tasks. Решта читається
пагінацією. `events_after` — межа цього огляду, а не підтвердження старих повідомлень.
Нова identity перевіряє inbox і починає replay із 0; відома — зі збереженого курсора.

Для щоденної роботи є bounded `agent-context`, повні `resources/{collection}/{id}`
і literal search. Вони використовують той самий authenticated read context;
sections мають totals/has_more й не підтверджують доставку. Outbox показує лише
власні вихідні доручення й receipt конкретного адресата. Повний сценарій:
[AGENT-WORKFLOW.md](AGENT-WORKFLOW.md).

## MCP і майбутні адаптери

Перший адаптер — локальний stdio MCP-процес, який звертається до віддаленого API.
Це дозволяє обійти відмінності підтримки remote MCP auth між клієнтами. Локальними
залишаються лише credential, курсор споживача та його робочі файли.

Агент може читати inbox і викликати `wait_events` між кроками. Для автоматичного
передавання подій у контекст потрібен hook/API конкретного host. Такий адаптер
підписується на сервер, зберігає доставку та використовує підтримуваний host-механізм.
Підтримку runtime injection і wake-up потрібно перевіряти для кожної інтеграції.
Час останнього мережевого контакту не слід показувати як доказ активності моделі.

Перша реалізація такого адаптера — `team-sync-agent`: окремий receiver, приватний
SQLite-кеш, outbox підтверджень і незалежні форматери Codex/Claude Code.
Для власних runtimes є версійований JSONL bridge. Серверний курсор комітиться
разом із локальним вмістом до `received`; cursor emission ведеться окремо для кожної
сесії. `processed` не встановлюється автоматично. Hook читає кеш без мережі й не
пробуджує idle session. JSONL delivery використовує окремий delivery ID: читання
не рухає cursor, а явний ack комітить його атомарно. Повторний ack ідемпотентний.
Повний контракт: [AGENT-PROTOCOL.md](AGENT-PROTOCOL.md); рішення й сумісність:
[ADR](adr/0001-heterogeneous-agent-delivery.md).

Межа відповідальності host описана в [архітектурі MCP](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture):
протокол передає контекст, а застосунок вирішує, як використовувати його з моделлю.

## Файли

Передача файла явна. Сервер потоково записує його з обмеженням розміру, обчислює
SHA-256 і публікує під незмінним content address у namespace проєкту. Спочатку
зберігаються байти, потім транзакційно — метадані й подія. Збій між цими кроками
може залишити непов'язаний blob; майбутня збірка сміття видаляє його після grace
period. Поточні записи не повинні посилатися на ще не опубліковані байти.

Повтор upload із тим самим `Idempotency-Key`, іменем і вмістом повертає той самий
Artifact. Інший вміст із тим самим ключем дає 409. MCP-завантаження перевіряє хеш
і створює новий локальний файл без перезапису наявного.

Штатне сховище v1 — файлова система одного сервера/спільний volume. Кільком API
реплікам потрібне спільне сховище байтів. Заміна на S3-compatible storage не змінює
UUID, хешів і API. Backup охоплює PostgreSQL разом із файлами.

Спільне редагування коду надалі працює через Git commits/patches. Система не
дзеркалить довільні локальні каталоги й не виконує автоматичне злиття файлів.

## Межі першої версії

Є API, MCP bridge, web UI, події, базова авторизація, leases, флаги й артефакти.
Web UI за `/` — статичні ES-модулі, що постачаються в Python-пакеті та працюють
через той самий API. Серверних доменних правил у frontend немає. Node потрібен
лише для frontend-тестів. IDE hooks, OAuth, групові запрошення, фільтри підписок,
інтеграції платформ, планувальник LLM і Git workflow розвиваються поверх ядра.
`/docs` залишається технічною документацією API.

Браузер використовує long polling. Після одноразового підключення за приватним
файлом, capability link або Bearer сервер зберігає доступ у 7-денному HttpOnly,
SameSite=Strict cookie, scoped до проєкту й identity. На HTTPS додається Secure.
Посилання містить credential у fragment, який очищається до першого запиту.
У localStorage/sessionStorage — лише UUID й назви, не токени. Кожна вкладка
зберігає власну identity; cookie-мутації потребують same-origin Origin і окремого
header. Bearer API довільних CLI не змінено. Персональних акаунтів не додаємо.
Курсор просувається після успішного оновлення відповідних колекцій; повтор
невідомої команди зберігає її ключ. CSP не дозволяє inline-скрипти, зовнішні
дані рендеряться як текст. Деталі й сумісність — у [ADR 0002](adr/0002-agent-workspace-and-browser-access.md).

HTTP доступ за межами локального хоста організовується через TLS reverse proxy.
Compose публікує API лише на loopback, PostgreSQL назовні не публікується.

## Перевірка фундаменту

Інтеграційні тести використовують PostgreSQL із початковою Alembic-міграцією.
Вони перевіряють міжпроєктні посилання, ролі, відкликання доступу, конкурентне
взяття роботи, takeover та відмову старому виконавцю, rollback і повтори команд,
флаги, receipts, незмінність файлів, replay, SSE reconnect і два окремі stdio MCP
процеси, підключені до одного HTTP-сервера. Є окреме
[живе приймання Claude Code і Codex-субагентів](LIVE-ACCEPTANCE.md) та UX-прогін
нових typed tools. Фізичні пристрої, Windows/macOS і нативний Codex CLI hook
trust/model flow залишаються окремими перевірками.
