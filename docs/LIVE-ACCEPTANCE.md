# Живе приймання Claude Code і Codex

Дата: 2026-11-01. Результат: **пройдено**.

Це окремий запуск із реальною роботою моделей, а не емуляція відповідей у тестах.
Використано новий синтетичний CTF, окремі credentials і робочі директорії.
Існуючі CTF та глобальні налаштування клієнтів не змінювалися.

| Учасник | Роль | Підключення |
| --- | --- | --- |
| Codex collaboration subagent | Координатор | Справжній stdio MCP bridge → HTTP API |
| Claude Code 2.1.252, `claude-sonnet-5` | Виконавець | stdio MCP, receiver, нативні lifecycle hooks |
| Другий Codex collaboration subagent | Незалежний спостерігач | Звичайний HTTP через httpx, без MCP |

## Сценарій і результат

1. Координатор створив challenge, пов'язане завдання та незмінний JSON-артефакт.
   Артефакт містив випадкові фрагменти з кодуваннями base64, hex і rot13.
   Правило флага: `CTF{sha256(UTF8(fragment1 + "|" + fragment2 + "|" + fragment3))}`.
2. Координатор надіслав Claude приватне повідомлення з UUID ресурсів, правилом
   обчислення й випадковим маркером. Відповідь залишалася в його приватному checker.
3. Claude отримав контрольний маркер через нативний `SessionStart` hook і створив
   знахідку з цим маркером **до першого читання inbox**.
4. Claude взяв завдання, завантажив файл через MCP із перевіркою SHA-256,
   обчислив відповідь локальним Python, опублікував evidence і флаг зі статусом
   `unverified`, завершив завдання та відповів координатору приватно.
5. Окремий маркер, надісланий після ініціалізації активної сесії, з'явився в
   `PreToolUse` hook. Claude записав його в знахідку до наступного читання inbox.
6. Координатор незалежно перевірив відповідь і авторство результатів. Лише після
   цього виконав `flag.verify`: `confirmed`, `local_checker`, з evidence.
   Це локальна перевірка синтетичного завдання; відправлення на CTF-платформу не було.
7. Координатор надіслав приватне підтвердження з новим маркером. Claude отримав
   його через hook, записав спостереження та явно підтвердив `processed`.
8. Незалежний Codex-спостерігач сам завантажив серверний артефакт через HTTP,
   перевірив SHA-256 та обчислив флаг. Перевірив завершення, assignee, evidence,
   історію підтвердження й авторство координатора. Приватне повідомлення повернуло
   йому `404`; спроба створити завдання — `403` без запису. Inbox спостерігача
   не містив приватного обміну інших учасників.

Завдання, файли, результати й приватні відповіді передавалися через Team Sync.
Спільна локальна директорія не використовувалася як канал передачі відповіді
між учасниками. Координатор і спостерігач мали власні незалежні обчислення.

## Виявлена проблема запуску та відновлення

Перший Claude-процес зупинив роботу: тестова конфігурація дозволяла команду
`python`, а модель викликала `python3`. У режимі `dontAsk` цей виклик був
заборонений. Водночас Claude завершив процес із кодом `0` і текстом запиту
дозволу. Тому успіх CLI-процесу сам по собі не є критерієм виконання завдання.

Для повторного запуску harness явно дозволив обидва конкретні інтерпретатори;
режим обходу permissions не вмикався. Нова сесія тієї самої identity прочитала
спільний стан, поновила lease й завершила початкове завдання. Нового завдання
чи другого claim не створювали. Це також перевірило відновлення після завершення
модельної сесії. Продуктовий код для цього виправляти не знадобилося.

## Як повторити

Це ручне, опційне приймання, яке використовує доступ до моделей і їхні квоти.
Воно не запускається в звичайному CI.

1. Запустити сервер, створити новий тестовий CTF і три identities:
   `coordinator`, `worker`, `observer`.
2. Для кожного учасника налаштувати власні `TEAM_SYNC_URL`,
   `TEAM_SYNC_PROJECT_ID`, `TEAM_SYNC_TOKEN` і приватну робочу директорію.
   Передавати токени через environment або приватну конфігурацію, не prompt.
3. Підключити координатору MCP; незалежному спостерігачу надати HTTP API.
4. Для Claude запустити `team-sync-agent --state <private-cache> watch`.
   Згенерувати його hooks через
   `team-sync-agent --state <private-cache> hook-config --host claude-code`.
   Передати цей файл через Claude `--settings`, а MCP-конфігурацію через
   `--strict-mcp-config --mcp-config <private-config>`.
5. Запускати Claude у виділеній директорії з `--setting-sources ""`,
   `--permission-mode dontAsk`, явним списком дозволених MCP tools, Read і
   потрібних Python/Python3 команд. Для спостереження hooks використати
   `--output-format stream-json --verbose --include-hook-events`.
   Обмежити витрати через `--max-budget-usd`; за потреби вимкнути збереження
   сесії через `--no-session-persistence`. Bare mode для цього сценарію не
   використовувати: він пропускає hooks і subscription auth.
6. Доручити учасникам наведений вище сценарій. Надіслати випадковий контрольний
   маркер до запуску Claude й інший — після його ініціалізації. Не передавати
   ці маркери в prompt моделі. Попросити її записати hook-спостереження до inbox.
7. Перевірити серверний стан і порядок подій у приватному Claude transcript:
   `hook_response` з маркером → `finding.create` → `inbox`. Для активного
   маркера додатково перевірити його відсутність у `SessionStart` цього запуску.
   Перевірити `processed` обох сторін, історію флага та незалежний checker.

Точні tool names у перевіреному Claude-запуску мали префікс
`mcp__team_sync__`; це ім'я MCP server у його локальній конфігурації.
Зміна імені server потребує відповідної зміни allowlist.

## Збережені докази та межі

Санітизований [машинний звіт](acceptance/live-2026-11-01.json) містить
20 перевірок контролера, UUID синтетичних ресурсів і точну область приймання.
Координатор додатково виконав 7 перевірок, незалежний спостерігач — 17;
вони частково перекриваються й не є новими автоматизованими тестами.

Повні transcripts, receiver cache, participant scripts і доступ до тестового
CTF залишено локально в gitignored `.team-sync/live/bda69461bbc4/`.
Owner-доступ — у приватному `access.json`; credentials і transcripts не
публікуються. Серверний тестовий CTF збережено для огляду через вебінтерфейс.

Усі учасники працювали на одному фізичному Linux-хості з різними identities.
Codex тут — реальні collaboration subagents поточної Codex-сесії; це **не**
перевірка hooks/trust flow окремого `codex exec`. Нативні Codex CLI hooks,
Windows/macOS, два фізичні пристрої та тривале навантаження залишаються окремими
перевірками. Доставка через hooks потребує lifecycle checkpoint; пробудження
idle-сесії та переривання запущеного інструмента не заявляються.

Схеми запуску звірено з офіційними джерелами:
[Claude Code non-interactive mode](https://code.claude.com/docs/en/headless),
[Claude Code hooks](https://code.claude.com/docs/en/hooks),
[Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode),
[Codex hooks і trust](https://learn.chatgpt.com/docs/hooks).

`.team-sync/review-live/v03/`. Тест не доводить автоматичного пробудження host:
другий запуск явно ініціював harness.
